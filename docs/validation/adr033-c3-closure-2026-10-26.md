## 1. Closure question and conclusion

C3 asks whether the real Claude Code host (a) leaves files unchanged when the ADR-033 operational hook refuses an edit, (b) delivers the refusal to the model and, in the scoped interactive arm, the user, and (c) preserves required proceed, block and non-guarantee boundaries. A hook exit code alone is not proof.

**Proposed verdict: C3 scope SATISFIED, subject to the precise coverage and exceptions below.** On Windows 11 with Claude Code 2.1.303 and model claude-opus-5-5, live Write and Edit runs show the specified operational refusals and decision-violation blocks, the specified proceeds, and operator-visible R-1/P-2 messages. For the subsequent AUTHORIZED-phase headless and interactive runs, the imported Mneme runtime was pinned to **b0dc1a14**. All claims are scenario-specific; this is neither a universal fail-closed guarantee nor a retrospective reclassification of failures.

## 4. Evidence standard and delivery ceiling

The primary records apply E1 outside-observer file hashes, E2 matching host tool use/result, E3 hook exit and output, verifier state and commit, E4 Git-call and OS-capture corroboration where required, E5 fixture history, E7 pins, E8 controls and E9 repeated probes. The four final PRs report checked redacted manifests, retained raw operator artifacts and no retrospective reclassification. The closure review should judge those reports and any spot checks against the accepted scope, not infer success from a batch summary line.

**Three delivery levels must remain separate:**
1. **Hook emitted:** the hook's own E3 output.
2. **Model delivered:** the real host's matching error tool result (or the bounded F-R2 model-bound additional-context proof for an UNVERIFIABLE proceed).
3. **User visible:** established only by #671 Q2's four interactive sessions, using the operator's copied terminal-log reply and attestation, **not video** or independent screen observation.

The R-3 proof is narrower than “any rollback”: a valid nonempty two-event prefix of a three-event fixture declaration, with exact content equality to the earlier REVOKED baseline. The #632 OS capture's github.com observation is not verifier-exclusive; attribution relies on the separately recorded wrapper Git endpoint calls.

## 5. Failures, limitations and non-guarantees that survive closure

- **F-R1 (permanent historical evidence):** #601 R-1 Edit-2 failed. A transient DNS problem caused AUTHORIZATION_UNVERIFIABLE, the hook proceeded and the edit landed. That is allowed by accepted **Architecture A**; revalidation #620 does not erase or turn it into PASS. No availability fail-closed promise holds when the verified baseline is unreachable.
- **F-R2 (historical defect, separately corrected):** the earlier exit-0 diagnostic was not model-delivered. The later #616 proof established model-bound additional-context delivery at its own pin, with controls; it did **not** change F-R1's proceed rule or prove interactive delivery of an UNVERIFIABLE diagnostic.
- **F-R3-1 (unchanged):** invalid empty local event history can be labelled BEHIND rather than INVALID. The #624 harness guard and phase-4 R-3 case prevent a false rollback proof without modifying the frozen runtime; no runtime fix is claimed.
- **Local enrollment is removable:** deleting the local declaration silently disables the opt-in verification trigger. Removing the hook or modifying certain repository configuration likewise defeats the intended protection. D-1/D-2/D-5 are observed limitations, not protection passes.
- **H-2 host timeout:** on this pinned host, an exceeded hook timeout let edits proceed. H-1 launch failure blocked, but the two observations cannot be generalized as reliable host fail-closed behavior.
- **Authorization authority:** fixture PRs and operator-script authorizations are owner-attested; neither zero-review fixture merges nor locally retained operator scripts constitute independent review.
- **Coverage ceiling:** no claim for MultiEdit, Bash, Stop, CI/C4, other host versions or platforms, private remote verification, arbitrary shell/adversarial full OS control, untested interactive rows, or future architecture. The C3 test fixture is public and controlled, not representative of every deployment.

## 6. Proposed closeout decision (review gate)

Accept **C3 validation coverage as complete within the approved, version-pinned scenario matrix**, with the deliberate P-6 pin qualification and all original failures and non-guarantees preserved above. Close the **C3 milestone**, not ADR-033 as a general safety guarantee. No change to mneme/, the matrix, fixture, the accepted ADR or the Layer 1 freeze is proposed. **C4 (CI) is a separate scope and requires its own authorization.**

Before accepting closure, the owner should confirm that (i) the merged PRs and exact commits in section 2 are correct; (ii) the sample-level and published manifest evidence is sufficient under the accepted C3 protocol; (iii) the P-6 historical pin qualification is explicit; and (iv) #601's FAIL and H-2's host-timeout proceed remain visible in the final verdict.

**Decision remains pending.** No subsequent test, release, fixture mutation or C4 execution is authorized by this closure proposal.
