## 4. What this establishes

- **F-R2 delivery on the pinned host:** on Claude Code 2.1.303, headless, an
  UNVERIFIABLE proceed puts Mneme's factual diagnostic in a model-bound
  transcript entry (H1 rule R1), at the attempted edit, without blocking it.
  - This holds in 4 of 4 runs (8 of 8 counting the first pass).
  - The classifier passes only on the R1 attachment (#611 review correction).
- **No false trigger:** under AUTHORIZED, and without a local declaration, the
  hook writes nothing to stdout and no diagnostic appears (§17.2 "Not
  triggered by").
- **No detected host difference:** the R3 pair comparison detected no
  difference from either control in the compared stream-json `system` event
  subtypes or permission indicators. That is the full extent of what the pair
  classifier checks.
- **Supporting, not proof:**
  - In D-2 the model's final reply quotes the diagnostic and explains that the
    edit went through unverified (an `echo`).
  - The text also appears in a `rendered` copy of the attachment and in the
    API request entries. These are classed `unclassified` and are not
    published.

## 5. What this does not establish

- **User-visible delivery:** `user_visible` is `not_tested` in every outcome.
  `systemMessage` stays unauthorized (§17.7).
- **F-R1:** unchanged. Any UNVERIFIABLE reason, including a transient DNS
  failure as in R-1 Edit-2, still lets the edit proceed. F-R2 only makes this
  visible to the model.
- **Other cases:** other UNVERIFIABLE reasons live (U-1/U-3 need a network
  block and were not run), other hosts, versions, interactive mode, warn
  mode, and the §17.3 `defer` case.
- **Batch R:** stays stopped. #601 is not rewritten.

## 6. Findings for review

- **F-FR2-1 (E4 traffic):** `api.github.com` appears in three of the four D-2
  captures. The wrapper shows that Mneme's verifier made no remote request in
  D-2 (no endpoint, config read only), and no forbidden host appears. From the
  available evidence, this is host traffic not attributable to the Mneme
  verifier. The capture does not identify which process generated it.
- **F-FR2-2 (collection, fixed in this PR):** the #611 collector would have
  published whole session transcripts. They carry Claude Code's system prompt,
  tool and agent listings and model thinking (about 190 KB each).
  `collect_redacted.py` now publishes `transcript.selected.jsonl` under the H1
  selection rule (`collect_h1.py`): user and assistant entries with thinking
  omitted, plus every `hook_*` attachment. `MANIFEST.json` records the raw
  transcript's SHA-256 and size and counts the entry types not published. The
  collector also gained `--probes`/`--extra` selection, needed because this
  live root also holds Batch R's probes, and `<HOST>` redaction. Apart from the host-name redaction, its output for
  non-transcript files is unchanged when the new flags are not used.
- **F-FR2-3 (pin drift after the run):** #613 (`b0dc1a14`, ADR-034 F-1)
  merged after this run and changes `mneme/` (`cli.py`, `enforcer.py`,
  `integrations/claude_code/hook.py`).
  - This run is unaffected: every probe's observer recorded `mneme/` identical
    to `5a20b360`, at harness `b3f1e7fa`.
  - Any later live C3 run against current `main` fails the preflight until
    `PIN_MNEME_BASE` is moved, in its own reviewed change.
  - The offline self-test for this PR was run against a detached checkout at
    `5a20b360`.
- **Residual path:** Claude Code's project-folder slug
  (`<HOME>\.claude\projects\C--dev-mneme-c3-live-<probe>-repo`) remains in
  `events.jsonl` and `hook-log.jsonl`. It derives from the documented live root
  `/c/dev/mneme-c3-live` (`pins.env`), not from personal data.
