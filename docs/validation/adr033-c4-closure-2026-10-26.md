## 1. Closure question and conclusion

C4 asks whether a GitHub required check can apply ADR-033's explicit
availability policy while keeping deterministic decision enforcement and the
CI1 trust boundary: trusted results keep their strict/warn meaning, operational
UNEVALUATED follows an administrator-set `open|closed` posture and is never a
PASS, and changes to decision memory or the trusted CI surface are refused
under every posture.

**Verdict: AC1-AC8 met; AC9 met by the documentation changes in this PR.**
Offline, the pinned adapter reproduced every Gate 0 matrix row against the
CI1-approved evaluator (Gate 2). Live, in the isolated CI1 lab, GitHub
permitted or refused head-pinned merges exactly as specified for L1-L5 (Gate 3).
All claims are bounded to the evidence below. This is not a general fail-closed
guarantee, not a production deployment, and not an ADR-029 "relevant
enforcement observed" claim (§4).

## 5. ADR-029 assessment

ADR-029 §2 requires all six dimensions (control/provenance, subject, decision,
rule, applicability, outcome) bound to the same evaluation, by deterministic
identifiers, failing closed.

- **L5 and L1:** decision, rule and applicability are bound inside the
  evaluator's own output (`ADR-901`, `decision_version_id` `dver-d3d431ff…`,
  rule `ADR-901:FORBID_LITERAL:1eff1b82…`, `APPLIED` via `docs/**`). The outcome
  is bound at rule level (FAIL / PASS), and to GitHub's 405 / 200 only through
  joins (check run → workflow run → artifact). Control/provenance and subject
  are stronger than in CI1: the report carries the adapter SHA-256, evaluator
  commit and wheel hash, head SHA, merge-base and per-file content SHA-256. But
  these are recorded by the adapter from workflow inputs, not emitted by the
  evaluator; the evaluator payload carries only `input_path`.
- **L2-L4:** no evaluator payload; at most execution observed.

**Conclusion: "relevant enforcement observed" is not claimed.** L5 and L1 are
execution observed with near-complete binding, the same cross-record pattern
CI1.4 recorded as partial. Upgrading them would need an explicit owner ruling
that adapter-recorded provenance from a hash-pinned trusted adapter satisfies
ADR-029, which is outside this closure.

## 7. Limitations and non-guarantees that survive closure

- **Administrative trust (P7/P8).** An administrator, or an agent token with
  administrator rights, can change the ruleset, workflow, Actions policy or
  posture variable. The Gate 3 bootstrap needed a ruleset disable, which is
  exactly such an operation.
- **Not exercised live:** adapter pin mismatch, runner or bootstrap failure,
  host timeouts outside the job, merge races, posture fallback.
- **Posture change does not re-run checks;** a head green under `open` stays
  green until re-run.
- **Decision step shares code with the evaluation step;** it catches an
  inconsistent or tampered report, not a defect common to both. Its evaluator
  identity check compares workflow constants with themselves.
- **ADR-034 numeric or `subject` payload records are classed UNEVALUATED,** so
  under `open` such a payload could pass even if it contained a FAIL. The
  pinned `0b74d410` evaluator emits neither; this must be revisited before any
  evaluator change.
- **Coverage:** literal-tier rules, include-selector scope, the CI1 corpora and
  the Gate 0 matrix; no Unicode normalization matching of protected paths.
- **Platform:** Gate 2 ran in an `ubuntu:24.04` container on Windows/WSL2, not
  a GitHub runner; Gate 3 ran on GitHub in the lab only, before GitHub's
  2026-11-02 `pull_request_target` change.
- **CI1 limits unchanged:** no governed decision-update route, partial ADR-029
  binding, Core's `mneme-check.yml` still an implicit `open` (ADR-033 §5),
  production rollout restrictions.
- **C3 limitations unchanged:** R-1 Edit-2 FAIL, Architecture A
  verifier-unavailable proceed, F-R2 history, F-R3-1, removable local
  enrollment, H-2 timeout proceed, MultiEdit N/A, P-6 earlier runtime pin and
  operator attestation.
- **Owner instructions** across Gates 0-4 were recorded on the owner's behalf
  from the Mneme Core conversation, not as separate GitHub reviews.

## 8. Closure decision and boundaries

On merge, C4 is closed as a **bounded CI availability-policy implementation and
validation milestone** (Gate 0 §10). Closure does not:

- deploy anything to Core's production CI or change its required checks,
  rulesets or Actions policy;
- remove CI1 promotion conditions or establish general enforcement safety;
- claim ADR-029 relevant enforcement observed;
- unarchive the CI1 lab or authorize further lab work.

Any production adoption needs its own rollout decision and Layer 1
authorization. Changing the evaluator pin needs a new parity proof and owner
approval (Gate 0 A5).
