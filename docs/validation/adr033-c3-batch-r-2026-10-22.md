## 3. What this establishes

**First live evidence of fail-closed enforcement on a real host:** in 3 of 4
R-1 runs, with a verified `AUTHORIZED` baseline and canonical memory missing,
Claude Code 2.1.303 did not apply a compliant `Write` or `Edit`. The file
stayed byte-identical, by an outside observer's hash. The operational refusal
reached the model as a tool error. The verifier contacted only the fixture
URL.

It does not establish: R-2..R-7, the controls, user-visible delivery, other
hosts or versions, or MultiEdit.

## 4. The R-1 Edit-2 failure (root cause)

- **What happened.** The verifier's `git ls-remote` failed with `fatal: unable
  to access '…': Could not resolve host: github.com`. The verifier mapped it
  to `AUTHORIZATION_UNVERIFIABLE(DNS)` in 0.26 s. No `github.com` handshake
  appears in that probe's capture.
- **Mneme behaved as specified.** Under Architecture A an unverifiable baseline
  means **no availability refusal** (ADR-033 §4.3, C2b §5.3 R2). The hook
  proceeded (exit 0), and Claude Code applied the edit. This is the disclosed
  "verifier denial" limit (C2b §13), here caused by an accidental transient
  DNS failure on the operator host rather than an adversary.
- **The visible proceed was not visible.** The hook emitted
  `mneme-hook: availability AUTHORIZATION_UNVERIFIABLE(DNS); evaluation=NOT_RUN;
  availability did not refuse.` on stderr with exit 0. The `tool_result`
  Claude Code returned contains only "The file … has been updated
  successfully." The proceed diagnostic was **emitted but not delivered to the
  model**, consistent with the earlier A1 `NOT_DELIVERED` finding for exit-0
  hook output. ADR-033 §4.3's "visible proceed" is not met on this host.
- **Cause of the DNS failure: unexplained.** It was transient: the three probes
  either side resolved `github.com` normally, and Claude Code's own model calls
  in the same probe succeeded. The per-probe `pktmon` start is a possible
  contributor and is not asserted.

## 5. Findings for review

- **F-R1.** A single transient DNS failure let an edit through that a
  verified-AUTHORIZED repository should have refused. That matches the
  accepted Architecture A design, but it shows the guarantee depends on
  verification being reachable at every edit (no cache, about 2–3 s per
  verification).
- **F-R2.** The visible-proceed diagnostic does not reach the model on this
  host: exit-0 stderr is dropped. Anyone relying on ADR-033 §4.3 visibility
  would not see the fallback.
- **F-R3.** The gate worked: it stopped after one unexpected result, and the
  evidence is preserved unaltered.

Any decision on F-R1/F-R2 (for example whether to re-run R-1, or whether
the U-batch expectations need revisiting) belongs to the owner. This record
makes none.
